# Продвижение объявлений (Paid Promotion)

## Обзор

Функционал продвижения объявлений позволяет пользователям продвигать свои объявления, чтобы они отображались выше в результатах поиска. Продвигаемые объявления визуально выделяются и имеют приоритет в ранжировании.

**Статус:** ✅ MVP полностью реализован

## Важные правила

1. **Продвигать могут только авторизованные пользователи:**
   - Все endpoints для продвижения защищены `@UseGuards(JwtAuthGuard)`
   - Только пользователи с валидным JWT токеном могут продвигать объявления
   - Админские endpoints дополнительно защищены `AdminGuard`

2. **Продвигать можно только активные объявления:**
   - Кнопка "Продвигать" отображается только для объявлений со статусом `Active`
   - На бэкенде проверяется: нельзя продвигать объявления со статусом `Paused` или `Closed`

3. **Продвижение сохраняется при переходе в паузу:**
   - Если продвигаемое объявление переходит в статус `Paused`, флаг `is_promoted` остаётся `true`
   - **Время продвижения не тратится в статусе "Пауза"** - отсчёт времени происходит только когда объявление в статусе `Active`
   - При возврате из паузы в статус `Active`, продвижение возобновляется с оставшимся временем
   - Продвигаемые объявления в статусе `Paused` не показываются в результатах поиска (только активные)

4. **Сроки продвижения:**
   - Продвижение может быть на 1, 7, 14 или 30 дней
   - Для админа доступен дополнительный вариант - бессрочно (`promoted_until = null`)
   - После истечения срока продвижение автоматически отключается (`is_promoted = false`)
   - В результатах поиска показываются только объявления с активным продвижением (не истёк срок)

5. **Сортировка:**
   - Сначала показываются продвигаемые объявления, отсортированные по выбранным правилам сортировки
   - Затем показываются остальные объявления, отсортированные по тем же правилам сортировки
   - Внутри каждой группы (продвигаемые/непродвигаемые) применяется одинаковая логика сортировки

6. **Автоматическое закрытие объявлений:**
   - Продвигаемые объявления с активным промо **не закрываются автоматически**, даже если они не обновлялись более 5 месяцев
   - Автозакрытие работает для непродвигаемых объявлений старше 5 месяцев
   - Когда промо истекает (`promoted_until < now`), при следующем прогоне автозакрытия такие объявления закрываются автоматически
   - При закрытии объявления (автоматическом или ручном) статус продвигаемого автоматически убирается

## Текущая реализация

### База данных

#### Таблица `listings`
Добавлены поля:
- `is_promoted` (boolean, default false) - флаг продвижения
- `promoted_until` (timestamp, nullable) - дата окончания продвижения (null = бессрочно)
- `promoted_started_at` (timestamp, nullable) - дата начала продвижения
- `promoted_paused_at` (timestamp, nullable) - дата входа в паузу (для заморозки времени)

#### Таблица `promotion_history`
Создана для хранения истории продвижений:
- `id` (uuid, primary key)
- `listing_id` (uuid, foreign key, ON DELETE CASCADE)
- `user_id` (uuid, foreign key, ON DELETE CASCADE)
- `listing_title` (varchar) - название объявления на момент создания записи
- `started_at` (timestamp) - дата начала продвижения
- `ended_at` (timestamp, nullable) - дата окончания продвижения
- `days` (integer) - количество дней продвижения
- `created_at` (timestamp) - дата создания записи

Индексы созданы на: `listing_id`, `user_id`, `started_at`, `ended_at`, `created_at`

### Backend API

#### Endpoints для пользователей

**`PATCH /api/listings/:id/promote`**
- Переключение продвижения для своего объявления
- Требуется авторизация (`JwtAuthGuard`)
- Валидация: только активные объявления, сроки 1/7/14/30 дней
- Лимит: `MAX_PROMOTIONS_PER_USER` активных продвижений на пользователя

**`GET /api/listings/promotion-history`**
- Получение истории продвижений текущего пользователя
- Пагинация: по умолчанию 50 записей на страницу
- Параметры: `page`, `limit`

**`GET /api/listings/promotion-history/check`**
- Проверка наличия истории продвижений у текущего пользователя
- Возвращает: `{ hasHistory: boolean }`

**`GET /api/listings/promotion-access`**
- Получение статуса доступа к функциям продвижения
- Не требует авторизации (`OptionalJwtAuthGuard`)
- Возвращает: `{ access: 'disabled' | 'admin' | 'all', enabled: boolean, isAdmin: boolean, canPromote: boolean }`
- Используется фронтендом для определения, какие UI элементы показывать пользователю
- Логика:
  - `PROMOTION_ACCESS=all` → `canPromote=true` для всех пользователей
  - `PROMOTION_ACCESS=admin` → `canPromote=true` только для админов
  - `PROMOTION_ACCESS=disabled` → `canPromote=false` для всех
  - В development админу всегда доступно независимо от `PROMOTION_ACCESS`

**`POST /api/listings/cron/disable-expired-promotions`**
- Cron endpoint для автоматического отключения истёкших продвижений
- Защищён секретным ключом `CRON_SECRET` (header `x-cron-secret`)

#### Endpoints для администраторов

**`PATCH /api/admin/listings/:id/promote`**
- Управление продвижением любого объявления
- Требуется авторизация и роль админа (`JwtAuthGuard`, `AdminGuard`)
- Поддерживает бессрочное продвижение (`days: null`)

**`GET /api/admin/promotions`**
- Получение всех продвижений с пагинацией и фильтрацией
- Параметры: `page`, `limit`, `listingId`, `userId`, `fromDate`
- Пагинация: по умолчанию 50 записей на страницу

**`GET /api/admin/listings`**
- Получение всех объявлений с фильтрацией по статусу и промо
- Параметры: `page`, `limit`, `listingId`, `userId`, `status`, `isPromoted`
- Серверная пагинация и фильтрация

**`GET /api/admin/users`**
- Получение всех пользователей с поиском и фильтрацией
- Параметры: `page`, `limit`, `searchQuery`, `roleFilter`
- Серверная пагинация и поиск

**`GET /api/admin/listings/status-counts`**
- Получение счётчиков объявлений по статусам и промо
- Используется для отображения чисел на фильтрах

### Frontend

#### Компоненты

- **`PromotionModal`** - модалка выбора срока продвижения (1, 7, 14, 30 дней + бессрочно для админа)
- **`PromotionHistoryModal`** - модалка истории продвижений с таблицей и пагинацией
- **`ListingCard`** - визуальное выделение продвигаемых объявлений (бордер, лейбл)
- **`ListingManagementCard`** - визуальное выделение и кнопки управления продвижением
- **`PromotionsTab`** - вкладка в админке с таблицей всех продвижений

#### Страницы

- **`/my-listings`** - кнопка "Продвигать", фильтр по промо, кнопка "История продвижений"
  - Кнопки и фильтры отображаются только если `canPromote === true` (проверяется через `GET /api/listings/promotion-access`)
  - Визуальное выделение промо объявлений (бордер, лейбл) работает для всех пользователей независимо от доступа
- **`/admin`** - вкладки "Объявления", "Пользователи", "Продвижения" с серверной пагинацией
- **`/favorites`** - сортировка: сначала промо по `updated_at`, затем остальные
- **`/listings/[id]`** - тег "Промовирано"

#### Визуальное выделение

- Бордер: 2px, цвет `#6eeb9c87` (зелёный с прозрачностью)
- Лейбл "Промовирано": золотой/жёлтый цвет (`border-yellow-500 text-yellow-400`) с иконкой короны
- Лейбл всегда первый в списке тегов
- На главной странице: компактные теги (только эмодзи) при наличии 3 тегов одновременно

## Переменные окружения

### Backend

```env
# Контроль доступа к функции продвижения
# Возможные значения: disabled, admin, all
# По умолчанию: disabled
PROMOTION_ACCESS=disabled

# Секретный ключ для аутентификации cron jobs
# Используется для защиты endpoints, вызываемых cron задачами
# Должен быть длинным случайным ключом (минимум 32 символа)
CRON_SECRET=your-secret-key-here

# Максимальное количество активных продвижений на одного пользователя
# Защита от злоупотреблений и перегрузки системы
# По умолчанию: 10
MAX_PROMOTIONS_PER_USER=10
```

### Примеры использования

1. **Отключить функцию для всех (production):**
   ```env
   PROMOTION_ACCESS=disabled
   ```

2. **Доступна только админам (production):**
   ```env
   PROMOTION_ACCESS=admin
   ```

3. **Доступна всем пользователям (production):**
   ```env
   PROMOTION_ACCESS=all
   ```

**Важно:** 
- Переменная `PROMOTION_ACCESS` учитывается только в production. В development (`NODE_ENV !== 'production'`) админу всегда доступна функция для удобства разработки и тестирования.
- Фронтенд получает статус доступа через `GET /api/listings/promotion-access` и показывает/скрывает UI элементы соответственно
- Визуальное выделение промо объявлений (бордер, лейбл) работает для всех пользователей независимо от `PROMOTION_ACCESS`

## Безопасность

### Аутентификация и авторизация

- Все endpoints защищены `@UseGuards(JwtAuthGuard)`
- Админские endpoints дополнительно защищены `AdminGuard`
- Проверка принадлежности объявления пользователю через `req.user.id`

### Валидация входных данных

- DTO валидация через `class-validator`
- Проверка формата UUID для всех ID параметров
- Валидация срока продвижения (только разрешённые значения: 1, 7, 14, 30)
- Проверка статуса объявления при включении продвижения

### Rate Limiting

- Глобальный лимит: 100 запросов в минуту (production)
- Специальные лимиты для endpoints продвижения:
  - `togglePromotion`: 10 запросов в минуту
  - `getPromotionHistory`: 30 запросов в минуту
  - Админские endpoints: 20-30 запросов в минуту

### Защита cron endpoints

- Endpoint `disableExpiredPromotions` защищён секретным ключом `CRON_SECRET`
- Проверка через header `x-cron-secret`

### Лимиты на количество продвижений

- Максимальное количество активных продвижений на пользователя: `MAX_PROMOTIONS_PER_USER` (по умолчанию 10)
- Проверка выполняется при каждом включении продвижения

### Инвалидация кэша

- При изменении статуса продвижения инвалидируется кэш поиска объявлений
- Используется `redisService.invalidateByPrefix(CACHE_PREFIXES.listingsSearch)`
- Также инвалидируется кэш конкретного объявления

## Примечания

1. **Визуальное выделение:**
   - Зелёный бордер (2px, цвет `#6eeb9c87`) для продвигаемых объявлений
   - Лейбл "Промовирано" всегда первый в списке тегов
   - На главной странице компактные теги (только эмодзи) при наличии 3 тегов одновременно

2. **Ранжирование:**
   - Продвигаемые объявления всегда показываются первыми
   - Внутри группы продвигаемых применяется выбранная пользователем сортировка
   - Внутри группы непродвигаемых применяется та же сортировка

3. **Производительность:**
   - Индексы на `is_promoted` и `promoted_until` для быстрой сортировки
   - Серверная пагинация на всех вкладках админки
   - Использование `useDeferredValue` для предотвращения мерцания UI

4. **Кэширование:**
   - При изменении статуса продвижения инвалидируется кэш поиска
   - Кэш конкретного объявления также инвалидируется

5. **Статус объявления:**
   - Продвигать можно только активные объявления
   - При переходе в паузу продвижение сохраняется, время не тратится
   - При возврате из паузы продвижение возобновляется с оставшимся временем
   - В результатах поиска показываются только активные объявления

6. **Автоматическое закрытие:**
   - Продвигаемые объявления с активным промо не закрываются автоматически
   - Когда промо истекает, при следующем прогоне автозакрытия такие объявления закрываются автоматически
   - При закрытии (ручном или автоматическом) статус продвигаемого автоматически убирается

7. **История продвижений:**
   - Все продвижения записываются в таблицу `promotion_history`
   - При закрытии объявления обновляется `ended_at` в истории
   - История сохраняется даже после удаления объявления (благодаря `listing_title`)

8. **Cron job:**
   - Endpoint для автоматического отключения истёкших продвижений создан
   - Требуется настроить cron задачу на сервере для регулярного вызова

9. **Контроль доступа через `PROMOTION_ACCESS`:**
   - Фронтенд получает статус доступа через `GET /api/listings/promotion-access`
   - UI элементы (кнопки "Промовирай", "История промо", фильтр "Промовирани") отображаются только если `canPromote === true`
   - Визуальное выделение промо объявлений (бордер, лейбл) работает для всех пользователей независимо от доступа
   - Логика работы:
     - `PROMOTION_ACCESS=disabled`: кнопки и фильтры скрыты для всех
     - `PROMOTION_ACCESS=admin`: кнопки и фильтры видны только админам
     - `PROMOTION_ACCESS=all`: кнопки и фильтры видны всем авторизованным пользователям
   - Backend дополнительно проверяет доступ при попытке использовать функционал (возвращает 403 если доступ запрещён)

## Важно: Мультирепозиторий и PPCSL

**При дальнейшей разработке необходимо учитывать:**
- Скоро будет переход на мультирепозиторий с выделением отдельно PPCSL (Platform for Posting Car Sale Listings)
- PPCSL будет core репозиторием, используемым как git submodule в других проектах
- При реализации нужно делать код так, чтобы его было удобно переносить в PPCSL
- Избегать жестких привязок к специфичным для текущего проекта вещам
- Использовать конфигурацию через переменные окружения и конфиг-файлы
- Документация по мультирепозиторию: `docs/MULTI_REPOSITORY_ARCHITECTURE.md` (включает обзор PPCSL)
