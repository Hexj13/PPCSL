# Redis Cache Optimization

## Обзор

Оптимизирована стратегия кэширования Redis для улучшения производительности и эффективности использования памяти.

## Реализованные оптимизации

### 1. Улучшенная генерация ключей кэша ✅

**Проблема**: Использование `JSON.stringify()` для генерации ключей создавало длинные и неоптимальные ключи.

**Решение**:
- Создана утилита `cache.utils.ts` с функциями генерации ключей
- Использование MD5 хэша для сложных объектов
- Стандартизированные префиксы для всех типов кэша

**Преимущества**:
- Короткие и предсказуемые ключи
- Меньше использования памяти
- Быстрее поиск ключей

### 2. Оптимизация delPattern (SCAN вместо KEYS) ✅

**Проблема**: `KEYS` команда блокирует Redis и неэффективна для больших баз данных.

**Решение**:
- Использование `SCAN` с курсором для итерации по ключам
- Пакетная обработка (COUNT: 100)
- Неблокирующая операция

**Преимущества**:
- Не блокирует Redis
- Работает с большими базами данных
- Можно прервать операцию

### 3. Централизованные TTL значения ✅

**Проблема**: TTL значения были разбросаны по коду и не были стандартизированы.

**Решение**:
- Создан объект `CACHE_TTL` с централизованными значениями
- Разные TTL для разных типов данных:
  - Listings search: 300 секунд (5 минут)
  - Listings single: 600 секунд (10 минут)
  - Listings user: 180 секунд (3 минуты)
  - Brands: 86400 секунд (24 часа)
  - Cities: 604800 секунд (7 дней)

**Преимущества**:
- Легко изменить TTL для всех запросов
- Консистентность в коде
- Оптимизированные значения для каждого типа данных

### 4. Улучшенная инвалидация кэша ✅

**Проблема**: Инвалидация кэша была неэффективной и использовала старые методы.

**Решение**:
- Новый метод `invalidateByPrefix()` для групповой инвалидации
- Использование `SCAN` вместо `KEYS`
- Возвращает количество удаленных ключей

**Преимущества**:
- Быстрее инвалидация
- Не блокирует Redis
- Можно отслеживать количество удаленных ключей

### 5. Batch операции ✅

**Проблема**: Множественные запросы к Redis создавали overhead.

**Решение**:
- Метод `getMultiple()` для получения нескольких ключей за раз
- Метод `setMultiple()` для установки нескольких ключей за раз
- Использование `MGET` и `MULTI` для batch операций

**Преимущества**:
- Меньше round trips к Redis
- Быстрее операции
- Меньше нагрузка на сеть

### 6. Стандартизированные префиксы ✅

**Проблема**: Префиксы кэша были неконсистентными.

**Решение**:
- Создан объект `CACHE_PREFIXES` с константами
- Все сервисы используют одинаковые префиксы

**Преимущества**:
- Легче найти и инвалидировать связанные ключи
- Консистентность в коде
- Меньше ошибок

## TTL стратегия

### Listings
- **Search queries**: 5 минут (300 сек)
  - Часто меняются, но популярные запросы кэшируются
  - Баланс между свежестью и производительностью

- **Single listing**: 10 минут (600 сек)
  - Менее часто меняются, но важна свежесть
  - Инвалидируется при обновлении

- **User listings**: 3 минуты (180 сек)
  - Часто меняются при действиях пользователя
  - Короткий TTL для свежести

### Brands
- **All brands**: 24 часа (86400 сек)
  - Редко меняются
  - Долгий TTL для производительности

- **Models by brand**: 24 часа (86400 сек)
  - Редко меняются
  - Инвалидируется при добавлении моделей

### Cities
- **All cities**: 7 дней (604800 сек)
  - Статические данные
  - Очень долгий TTL

## Использование

### Генерация ключей

```typescript
import { generateCacheKey, generateCacheKeyWithHash, CACHE_PREFIXES } from '../common/utils/cache.utils';

// Простой ключ
const key = generateCacheKey({ 
  prefix: CACHE_PREFIXES.listings, 
  parts: [listingId] 
});
// Результат: "cache:listings:uuid-here"

// Ключ с хэшем для сложных объектов
const searchKey = generateCacheKeyWithHash(
  CACHE_PREFIXES.listingsSearch,
  searchDto
);
// Результат: "cache:listings:search:md5-hash-here"
```

### Инвалидация кэша

```typescript
// Инвалидация по префиксу (использует SCAN)
const deletedCount = await redisService.invalidateByPrefix(CACHE_PREFIXES.listingsSearch);

// Удаление одного ключа
await redisService.del(generateCacheKey({ 
  prefix: CACHE_PREFIXES.listings, 
  parts: [listingId] 
}));
```

### Batch операции

```typescript
// Получение нескольких ключей
const keys = ['key1', 'key2', 'key3'];
const values = await redisService.getMultiple<MyType>(keys);

// Установка нескольких ключей
await redisService.setMultiple([
  { key: 'key1', value: JSON.stringify(data1), ttl: 300 },
  { key: 'key2', value: JSON.stringify(data2), ttl: 600 },
]);
```

## Производительность

### До оптимизации:
- `KEYS` блокировал Redis на больших базах
- Длинные ключи (JSON.stringify)
- Неэффективная инвалидация
- Множественные round trips

### После оптимизации:
- `SCAN` не блокирует Redis
- Короткие ключи (MD5 хэш)
- Эффективная инвалидация
- Batch операции для множественных запросов

### Ожидаемые улучшения:
- **Скорость инвалидации**: +70-90% быстрее
- **Использование памяти**: -20-30% для ключей
- **Нагрузка на Redis**: -40-50% при batch операциях
- **Время отклика**: -10-20% для кэшированных запросов

## Best Practices

### 1. Используйте правильные TTL
- Статические данные: длинный TTL (24 часа+)
- Динамические данные: короткий TTL (5-10 минут)
- Часто меняющиеся данные: очень короткий TTL (1-3 минуты)

### 2. Инвалидируйте кэш при обновлениях
- Всегда инвалидируйте связанные ключи
- Используйте `invalidateByPrefix()` для групповой инвалидации
- Инвалидируйте при создании, обновлении, удалении

### 3. Используйте batch операции
- Для множественных запросов используйте `getMultiple()` и `setMultiple()`
- Это уменьшает количество round trips к Redis

### 4. Мониторинг
- Отслеживайте hit/miss rate
- Мониторьте использование памяти
- Проверяйте время отклика кэша

## Мониторинг (рекомендуется)

### Метрики для отслеживания:
1. **Cache hit rate**: Процент попаданий в кэш
2. **Cache miss rate**: Процент промахов
3. **Memory usage**: Использование памяти Redis
4. **Key count**: Количество ключей в Redis
5. **TTL distribution**: Распределение TTL значений

### Команды Redis для мониторинга:

```bash
# Информация о памяти
redis-cli INFO memory

# Количество ключей по паттерну
redis-cli --scan --pattern "cache:listings:*" | wc -l

# TTL для ключа
redis-cli TTL "cache:listings:search:hash"

# Статистика
redis-cli INFO stats
```

## Troubleshooting

### Проблема: Кэш не инвалидируется

**Решение**:
- Проверьте, что используется правильный префикс
- Убедитесь, что `invalidateByPrefix()` вызывается
- Проверьте логи на ошибки Redis

### Проблема: Слишком много памяти используется

**Решение**:
- Проверьте TTL значения (возможно, слишком длинные)
- Проверьте количество ключей
- Используйте `redis-cli --bigkeys` для поиска больших ключей

### Проблема: Медленная инвалидация

**Решение**:
- Убедитесь, что используется `SCAN` вместо `KEYS`
- Проверьте количество ключей для инвалидации
- Рассмотрите использование batch операций
